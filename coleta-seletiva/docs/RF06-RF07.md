# Implementação dos requisitos RF06 e RF07

## RF06 — consulta de pontos e materiais

O `GET /api/pontos` agora realiza consulta paginada de pontos ativos e aceita os filtros opcionais:

| Parâmetro | Descrição |
|---|---|
| `nome` | Pesquisa parcial, sem diferenciar maiúsculas/minúsculas, no nome do ponto. |
| `municipio` | Pesquisa parcial no campo textual `endereco` do ponto. |
| `bairro` | Pesquisa parcial no campo textual `endereco` do ponto. |
| `materialId` | Retorna pontos que aceitam o material com esse ID. |
| `material` | Pesquisa parcial pelo nome de um material aceito. |
| `pagina` | Índice da página, começando em zero. Padrão: `0`. |
| `tamanho` | Quantidade de registros por página, entre 1 e 100. Padrão: `20`. |

Exemplo:

```http
GET /api/pontos?municipio=Lagarto&bairro=Centro&material=Papel&pagina=0&tamanho=20
```

A resposta é uma página Spring Data (`content`, `totalElements`, `totalPages`, `number`, `size`, etc.). Cada item de `content` contém o endereço, os horários, os dados do ponto e `materiaisAceitos`, incluindo nome, unidade de medida e orientação de preparo.

**Importante sobre o modelo atual:** `PontoColeta` armazena o endereço em um único campo textual (`endereco`). Para que os filtros `municipio` e `bairro` encontrem os pontos, o valor desse campo deve conter o município e o bairro (por exemplo: `Rua A, Centro, Lagarto - SE`). A implementação preserva o contrato de cadastro existente e não exige alteração de tabela para RF06.

`GET /api/pontos/{id}` também retorna os materiais ativos aceitos pelo ponto e as orientações de preparo.

## RF07 — administração de operadores

O operador possui `id`, `nome` e `email`. O e-mail é validado, normalizado para minúsculas e único. A associação operador–ponto é representada pela entidade `OperadorPonto`, com unicidade do par `operador_id` + `ponto_id`.

| Método | Endpoint | Finalidade |
|---|---|---|
| `POST` | `/api/operadores` | Cadastrar operador. |
| `GET` | `/api/operadores` | Listar operadores. |
| `GET` | `/api/operadores/{id}` | Consultar operador. |
| `PUT` | `/api/operadores/{id}` | Atualizar nome e e-mail. |
| `POST` | `/api/operadores/{operadorId}/pontos/{pontoId}` | Vincular operador a ponto ativo. |
| `GET` | `/api/operadores/{operadorId}/pontos` | Listar os pontos vinculados ao operador. |
| `DELETE` | `/api/operadores/{operadorId}/pontos/{pontoId}` | Remover o vínculo. |

Exemplo de criação:

```http
POST /api/operadores
Content-Type: application/json

{
  "nome": "Operador de demonstração",
  "email": "operador@example.org"
}
```

Exemplo de vínculo:

```http
POST /api/operadores/1/pontos/2
```

O cadastro ou vínculo duplicado retorna `409`; operador ou ponto inexistente retorna `404`; ponto inativo não pode receber novo vínculo e retorna `409`.

## Banco de dados

Executar uma vez o script `src/main/resources/db/atualizacoes/rf07_operadores.sql` no banco PostgreSQL já utilizado pelo projeto. O script cria as tabelas `operador` e `operador_ponto`, suas chaves estrangeiras, restrição de unicidade e índices. Ele pressupõe que a tabela `ponto_coleta` já exista.

## Limite relacionado a permissões

O RF07 especifica que um operador não deve atualizar solicitações de outro ponto quando houver controle de acesso implementado. O projeto enviado não possui autenticação/autorização. Por isso, esta implementação entrega o cadastro e os vínculos, mas não simula uma autenticação nem afirma aplicar essa restrição de acesso. A verificação deverá ser integrada quando o mecanismo de autenticação/autorização for desenvolvido.

## Testes incluídos

`Rf06Rf07HttpTests` cobre pesquisa com filtros e paginação, retorno dos materiais e orientações, limite máximo da página, cadastro de operador, e-mail duplicado, vínculo duplicado, listagem e desvínculo. Os testes usam o mesmo ambiente PostgreSQL configurado para os testes HTTP já existentes.
